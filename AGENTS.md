# actor-22-drug-safety-recalls-monitor - AI agent notes

Regulatory Medical Recalls & Drug Safety Monitor. Combines two independent, live-verified-open regulator feeds into one 18-field Unified Master Schema (UMS) stream:

- **FDA** - `https://api.fda.gov/drug/enforcement.json` (openFDA drug enforcement/recall API). Plain unauthenticated JSON GET, no proxy needed. Rate limits (verified live 2026-09-07): 240 req/min + 1,000 req/day without a key, 240 req/min + 120,000 req/day with a free key. `limit` caps at 1000/request (a `limit=1001` request returns a real HTTP 400 verbatim) - values above that paginate via `skip`. Dates are bare `YYYYMMDD` strings.
- **EMA** - `https://www.ema.europa.eu/en/documents/report/dhpc-output-json-report_en.json` (Direct Healthcare Professional Communications export, updated twice daily 06:00/18:00 CET). No REST API, but a genuinely structured, `robots.txt`-allowed JSON export - the closest EU analog to an FDA-style safety alert. One full-snapshot download per run; no server-side pagination or date filtering, so `maxItems`/`dateRange` are applied client-side after the download. Dates are `DD/MM/YYYY` strings.

Both sources' raw shapes are captured verbatim in `test/fixtures/*.json` from real live requests - never assume a field's shape without checking those fixtures or the source comments in `src/sources/*.ts`.

## V2 delta engine (added 2026-09-08)

This actor was one of 5 found on the account outside the original 9-actor V2 migration mandate (see `_audit/fleet_v2_reconciliation_report.md` in the portfolio root for the full discovery story). Before this pass it had a real, correctly-implemented named key-value store (`Actor.openKeyValueStore()`, not the run-scoped `Actor.getValue()`/`setValue()` bug found on a sibling actor the same day) but only flat seen-id tracking - `event_type` was a hardcoded constant per source, never actually computed from a diff.

- `src/fingerprint.ts`: `fdaFingerprintOf()`/`emaFingerprintOf()` compute a **pair** of hashes per record - `statusFingerprint` (over just `status`/`regulatory_outcome`) and `contentFingerprint` (over the record's other mutable fields, excluding identity fields already encoded in `record_id`). Keeping these separate is what lets `src/delta.ts` distinguish a genuine status transition from an unrelated content correction.
- `src/delta.ts`: `classifyFdaRecord()`/`classifyEmaRecord()` - no prior entry -> this source's own first-seen name (`SANCTION` for FDA, `NEW_LISTING` for EMA - a deliberate pre-existing distinction, preserved, not replaced with a generic term); `statusFingerprint` differs -> `STATUS_CHANGE`; `contentFingerprint` differs -> `UPDATED`; neither differs -> `SNAPSHOT_NO_DIFF`.
- `src/state.ts`: `Actor.openKeyValueStore('actor-22-drug-safety-recalls-monitor-delta-state')` - a NAMED store, deliberately not `Actor.getValue()`/`Actor.setValue()`. Those resolve to the store "associated with the current Actor run" per the Apify SDK docs (`node_modules/apify/dist/actor.d.ts`) - i.e. a fresh, isolated store every run, never shared across separate runs. A sibling actor in this fleet (`primer-actor`) shipped exactly that bug and had it caught by real cloud verification (two separate runs got two different Key-value store IDs) the same day this actor was audited - this actor was independently checked against the exact same bug and found clean.
- **No `CLOSED` event.** Neither FDA nor EMA is confirmed to ever remove a historical record from its feed, and this actor's fetch is always a bounded, newest-first top-N window (`maxItemsPerSource`) - never an exhaustive walk of either register - so there's no way to trustworthily detect "this record is gone" even if the sources did support it. See CHANGELOG.md for the full reasoning.
- **`onlyNew`'s meaning changed** (disclosed, not silent): it now means "new or changed since last run" (delivers `STATUS_CHANGE`/`UPDATED` too), not just "never seen before." See CHANGELOG.md.
- **No dual-floor/baseline-floor pagination-limiting mechanism** - that pattern (used elsewhere in this fleet) solves an unbounded-backlog problem this actor doesn't have, since both sources are always fetched as one bounded top-N call, never a paginated walk of a full historical register.

## Known footguns

- `mcp/searchDrugRecalls.ts` is deliberately OUTSIDE `tsconfig.json`'s `include` (`./src/**/*` only) - it's a separate MCP-tool entry point, not part of the `dist/main.js` build. `eslint.config.mjs` ignores `**/mcp` for the same reason (type-aware linting can't parse a file outside the TS project). Don't "fix" this by adding `mcp/` to either without first deciding how it's actually built/run.
- No local `Dockerfile` exists (and none is referenced in `.actor/actor.json`) - the original v1.0.2-1.0.6 builds succeeded via Apify's own implicit default Node.js build for the declared `templateId`. Don't add one without checking whether the existing implicit build still works first; `package.json`'s `"start": "node dist/main.js"` already assumes a `dist/` gets built server-side.
- `.actor/actor.json`'s `meta.templateId` says `"ts-crawlee-cheerio"`, but this actor uses plain `fetch()` (`src/http.ts`), not Crawlee/Cheerio at all - a leftover from initial scaffolding, harmless, not worth "fixing" since it has no functional effect on the build.
- The mandatory `regulatoryDataDisclaimer` (see `src/schemas.ts`) is a `z.literal()`, not a free-form string - any normalizer change that drops or mutates it fails validation immediately (by design, not a bug to work around).
